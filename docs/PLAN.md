# 내 가계부 개발 계획 (PLAN)

- 버전: 1.0
- 작성일: 2026-11-11
- 프로젝트명: **내 가계부** (`my-ledger`) — 개인용 애플리케이션이며 예시 프로젝트와 무관한 독립 개발
- 목표: 다중 계좌·할인 충전·임시 인출 후 보충·급여 주기별 현금흐름 예측을 지원하는 개인용 가계부
- 초기 배포: 단일 Docker Compose 애플리케이션 + 영속 SQLite 파일
- 확장 방향: Repository Port / DB Adapter를 통해 추후 PostgreSQL으로 이관

## 1. 제품 방향

제공된 예시 화면에서는 홈, 거래 내역, 통계, 매달 고정비, 목적별 적립 기능만 참고한다. 원본 프로젝트 이름과 브랜딩은 사용하지 않는다. 과거 소비 기록뿐 아니라 **앞으로 얼마를 쓸 수 있고 어떤 계좌를 얼마만큼 채워야 하는지**를 보여주는 것이 핵심이다.

### 핵심 원칙
1. **자금 이동과 소비 분리**: 은행→선결제 충전이나 A→B 계좌 이체는 소비 지출이 아니다.
2. **이중기입 원장**: 거래 1건의 모든 계좌 증감 합계는 0원이다. 시스템 계정(수입/지출/혜택/개시 잔액)을 사용한다.
3. **선결제 혜택 별도 추적**: 결제액과 충전액의 차이는 비현금 혜택이며, 충전금 사용 시 액면 소비액과 실질 부담액을 구분한다.
4. **보충 의무 명시적 생성**: 모든 이체에 보충 의무를 강제하지 않고, '임시 인출'로 지정한 거래만 추적한다.
5. **확정과 예측 분리**: 확정 거래, 예정 거래, 추정 지출을 명확히 구분한다.
6. **DB 격리**: 도메인/애플리케이션 서비스는 SQLite와 PostgreSQL의 라이브러리에 직접 의존하지 않는다.

## 2. MVP (P0)

| 작업 | 사용자 기능 | 완료 기준 |
|---|---|---|
| M1 | 여러 계좌 생성, 초기 잔액 설정, 계좌별 잔액 조회 | 합계와 개별 잔액이 원장과 일치 |
| M2 | 수입/지출/이체, 카테고리, 내역 조회 | 이체가 소비 지출로 집계되지 않음 |
| M3 | 할인 선결제 충전, 충전금 사용 | 90,000원 결제→100,000원 충전에서 혜택 10,000원 분리 |
| M4 | 임시 인출 및 계좌 보충 | 20만 원 인출 후 5만 원 보충 시 15만 원 미보충 표시 |
| M5 | 급여일 기준 주기, 예산, 정기 입출금 | 10/23~11/24와 같이 비월초 주기 선택 가능 |
| M6 | 미래 잔액/부족액 예측 | 이미 확정된 거래와 예정 거래 이중 계산 없음 |
| M7 | 홈, 거래, 계좌, 계획, 통계 화면 | 모바일 우선 반응형 UI |
| M8 | 인증 및 백업/복구 | 외부 공개 시 인증 필수, 복구 테스트 성공 |

## 5. 처음 만든 앱 골격의 구현 범위

실행 가능한 기본 기능을 지향한다: 계좌 생성, 초기 잔액, 수입, 지출, 이체, 할인 선결제 충전, 선결제 소비, 임시 인출/일부 보충, 요약/내역 조회, SQLite 백업. **예산/정기지출/미래 예측, 인증, 환불·취소, 충전금 소멸 처리는 아직 상세 문서에만 정의된 후속 작업**이다. 이 경계를 혼동하지 않는다.

## 6. 운영 정책

- 기본 서비스는 `127.0.0.1:3000`에만 노출한다. 외부 개방 전 반드시 인증, TLS, 보안 헤더, CSRF/권한 검증을 구현한다.
- SQLite 파일은 **로컬 Docker 영속 볼륨**에 둔다. NFS/SMB에 SQLite WAL DB를 올리지 않는다.
- SQLite는 단일 writer가 한 번에 기록한다. 단일 앱 컨테이너로 시작하며 수평 확장하지 않는다.
- 비동기 작업·대규모 동시 접속·네트워크 스토리지 공유가 필요해지면 PostgreSQL을 고려한다.
- 실제 데이터 도입 전 백업과 복구를 연습한다. SQLite 온라인 백업 API로 일관된 스냅샷을 만들고, 별도 스토리지로 복제한다.
