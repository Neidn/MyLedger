# 도메인 규칙 및 회계 불변식 (DOMAIN_RULES)

## 1. 금액 및 시간

- 통화는 초기 `KRW`. 금액은 **정수 원**으로 저장하고 `Number.isSafeInteger`를 검증한다. 금액 입력은 대부분 양수이고, 원장 금액만 `+/-`를 사용한다.
- DB의 `amount_krw`는 SQLite `INTEGER`/PostgreSQL `BIGINT` 또는 범위가 보장된 정수 타입을 사용한다. JS 안전 정수 범위를 넘는 값은 거부한다.
- 거래 발생 날짜 `occurred_on`은 한국 기준 `YYYY-MM-DD`, 기록 시각 `created_at`은 UTC ISO 8601 문자열이다.
- 예정일은 달력 날짜이며 날짜 계산에 서버의 로컬 타임존을 사용하지 않는다.

## 2. 핵심 용어

- **확정 거래**: 실제 발생하여 원장에 기록된 수입/소비/이체/충전.
- **예정 거래**: 정기 지출이나 향후 보충 등 아직 잔액을 변경하지 않는 미래 계획.
- **추정 거래**: 반복된 소비 패턴을 이용한 예측값. 확정/예정과 중복하지 않는다.
- **보충 의무**: 특정 자금의 임시 인출에 대해 명시적으로 등록된 상환 필요액.
- **목표 잔액 부족분**: 계좌 잔액이 목표보다 적은 차액. 보충 의무와 동일하지 않다.
- **실결제액**: 은행에서 충전 플랫폼으로 실제 빠져나간 금액.
- **액면 금액**: 플랫폼에서 쓸 수 있는 충전 잔액.
- **혜택**: 액면 금액에서 실결제액을 뺀 비현금 추가 사용액.

## 3. 이중기입 원장

한 거래 `T`에 속한 entries의 합:

`SUM(entry.amount_krw WHERE transaction_id=T) = 0`

- 실제 사용자 계좌(balance) = 모든 확정 원장 항목의 금액 합계.
- `SYS:income`, `SYS:expense`, `SYS:benefit`, `SYS:opening`은 원장 대변/차변 균형을 위한 시스템 계좌이며 사용자 자산 합계에 노출하지 않는다.

| 거래 | 원장 기록 | 당기 소비 | 비고 |
|---|---|---|---|
| 계좌 A에 급여 300만 원 입금 | A `+3,000,000`, SYS:income `-3,000,000` | 0원 | 수입 300만 원 |
| A에서 식비 2만 원 | A `-20,000`, SYS:expense `+20,000` | 20,000원 | 소비 |
| A→B 20만 원 | A `-200,000`, B `+200,000` | 0원 | 이체 |
| A에서 9만 원 결제로 P 10만 원 충전 | A `-90,000`, P `+100,000`, SYS:benefit `-10,000` | 0원 | 혜택 1만 원 생성 |
| P에서 3만 원 사용 | P `-30,000`, SYS:expense `+30,000` | 30,000원 | 부담액은 lot 원가 배분 |
| B 보충 5만 원 | A `-50,000`, B `+50,000` | 0원 | 보충 의무 5만 원 감소 |

**주의:** `SYS:benefit`는 은행 현금 유입을 뜻하지 않는다. 비현금 충전 혜택을 별도 통계로 계산한다.

## 4. 선결제 lot 관리

충전 입력: `paid > 0`, `face >= paid`, `bonus = face - paid`.

예시: 실결제 90,000 / 액면 100,000 / 혜택 10,000.

1. `prepaid_lots`에 face 100,000, paid 90,000, remaining_face 100,000, remaining_paid 90,000을 만든다.
2. 선결제 계좌에서 30,000원 소비 시 FIFO에서 `used_face=30,000`을 차감한다.
3. 원가 배분: `used_paid=floor(used_face × remaining_paid_before / remaining_face_before)`.
4. 사용 혜택: `used_bonus=used_face-used_paid`.
5. 마지막 사용 시 잔여 원가를 전부 배분하여 전체 반올림 차액이 누적되지 않도록 한다.
6. 잔여: face 70,000 / paid 63,000. 소비 액면 30,000 / 부담 27,000 / 혜택 3,000.
7. 서로 다른 lot의 원가/만료일은 섞지 않는다. 동일 거래가 여러 lot를 소비할 수 있다.

기본 정책은 FIFO. 실제 플랫폼이 '혜택 먼저 사용'이나 '유효기간 빠른 lot 먼저 사용'이면 Adapter가 아니라 **도메인 정책(PrepaidAllocationPolicy)** 을 교체한다.

후속 구현: 만료, 환불, 취소 시 원장/lot/할인 배분 역산을 기록하며 계좌 현금/비현금 출금 구분. 초기 스캐폴드는 해당 명령을 지원하지 않으므로 수동 재충전/환불을 임의 이체로 대신하지 않는다.

## 4-1. 신용카드 계좌 (`card`)

카드는 부채 계좌다. 잔액이 음수이면 그만큼 카드값이 남은 것이다.

| 거래 | 원장 기록 | 당기 소비 |
|---|---|---|
| 카드 생성, 기존 결제 예정액 15만 원 | 카드 `-150,000`, SYS:opening `+150,000` | 0원 |
| 카드로 식비 3만 원 | 카드 `-30,000`, SYS:expense `+30,000` | 30,000원 (결제 시점) |
| 은행 A에서 카드값 18만 원 납부 | A `-180,000`, 카드 `+180,000` | 0원 (이체) |

- 소비는 **카드로 결제할 때** 한 번만 잡는다. 카드값 납부는 이체이므로 이중 집계되지 않고, 은행 잔액은 실제 출금일에 줄어든다.
- 카드는 잔액 확인 없이 지출·선결제 충전의 출금 계좌가 될 수 있다(한도는 후속).
- 카드로의 수입, 카드에서 다른 계좌로의 이체(현금서비스), 카드로 보충은 거부한다.
- `cardOutstandingKrw` = 음수 카드 잔액의 절댓값 합. 자산 합계(`assetBalanceKrw`)는 카드 잔액을 포함하므로 카드값만큼 줄어든 순자산이다. 은행·현금 잔액(`liquid`)에는 포함하지 않는다.
- 보관은 다른 계좌와 같이 잔액 0원(카드값 완납)일 때만 가능하다.

## 5. 임시 인출 및 보충 의무

- 계좌 이체 시 `replenishment.dueOn` 등을 명시적으로 입력하면 **출금 계좌가 보호 대상 계좌**로 등록된다.
- 보충 의무는 인출 이체가 성공한 같은 DB 트랜잭션 안에서만 생성한다.
- `remaining = principal - repaid`, 항상 `0 <= repaid <= principal`.
- 보충은 실제 출금 계좌→보호 대상 계좌로의 이체를 기록하고 해당 의무의 repaid를 증가시킨다.
- 잘못 기록한 보충은 보충 거래를 취소(역거래)하면 `repaid_amount`가 줄어든다. 임시 인출 이체를 취소하면 의무도 취소(`cancelled_at`)되며, 보충 기록이 남아 있으면 먼저 보충 거래를 취소해야 한다.
- 같은 계좌에 입금되었다고 자동으로 의무를 줄이지 않는다. 어떤 인출을 갚는지 연결해야 한다.
- 목표 잔액은 현재 잔액과 비교해 별도 표시한다. 보충 의무와 자동으로 합산하지 않는다.
- 기한이 지났더라도 거래를 자동 생성하거나 차감하지 않는다. 알림으로만 표시한다.

## 6. 급여 주기 및 예측 정의 (후속)

- 급여일 `pay_day`가 매월 25일이면 대략 `10/25~11/24`가 한 주기다.
- `pay_day`가 해당 달 말일보다 크면 **그 달 마지막 날**로 보정한다(예: 31일 → 2월 28/29일).
- 사용 가능 현금(`liquid`)에는 은행/현금 등 자유 사용 가능한 자산만 포함. 보호된 저축/목적자금 및 특정 가맹점에서만 쓰이는 충전금은 별도 표시.
- 예상 은행 잔액 = 현재 자유 현금 + 미확정 예정 수입 - 미확정 예정 비용 - 예정 보충 이체 - 기타 미래 현금 이동.
- 예상 소비 = 확정 소비 + 해당 기간의 예정 소비 + 추정 소비(중복 제외).
- 개별 거래는 `planned_id`를 연결해 예정→확정으로 한 번만 반영한다.
- 예측은 산출 근거와 예상 적용 날짜를 함께 저장/표시해 결과를 설명 가능하게 한다.

## 7. 트랜잭션 경계 및 실패 처리

- 한 API 명령은 원장/잔액/lot/보충 의무를 **하나의 DB 트랜잭션**으로 저장한다.
- 잔액 부족, 동일 계좌 이체, 잘못된 타입, lot 잔량 부족 시 전체 롤백한다.
- 클라이언트 재전송 방지용 `Idempotency-Key`는 같은 요청의 중복 원장 생성 방지에 사용한다. 운영 단계에서는 payload 해시 비교까지 추가한다.
- 확정 거래를 물리 삭제하지 않는다. 거래 수정·취소는 연계된 **역거래**로 기록한다.
  - **취소**: 원거래와 같은 유형, 모든 원장 항목의 부호를 뒤집은 거래를 **원거래 날짜**로 기록하고 `reverses_transaction_id`로 연결한다(고유 인덱스로 한 번만 가능). 원거래가 속한 기간의 소비·수입은 0으로 상쇄된다.
  - 부수 효과도 되돌린다: 선결제 소비 → 사용한 lot의 액면·원가 복원 / 충전 → 미사용일 때만, lot 소진 처리 / 임시 인출 이체 → 보충 기록이 없을 때만, 의무 취소 / 보충 → `repaid_amount` 감소.
  - 거부: 초기 잔액(opening), 이미 취소된 거래, 취소 기록 자체, 보관된 계좌가 포함된 거래, 되돌릴 금액만큼 잔액이 없는 계좌(카드는 예외).
  - **수정**: 원거래 취소 + 원거래 원장에서 복원한 명령에 변경값(금액·액면·메모·항목·날짜)을 적용해 재등록. 하나의 DB 트랜잭션이라 재등록이 실패하면 원거래는 그대로다. 계좌·유형 변경은 취소 후 새로 등록한다. 보충 거래는 수정 불가(취소 후 재등록).
  - **유일한 예외**: 잘못 만든 계좌 삭제. 초기 잔액(opening) 외 거래와 보충 연결이 전혀 없는 계좌만 삭제할 수 있고, 그 계좌의 개시 거래(계좌 + `SYS:opening` 두 항목)와 개시 lot을 함께 지운다. 다른 거래에 영향이 없으므로 원장 합계 0이 유지된다.
- 계좌 보관(`archived_at`): 잔액 0원이고 이 계좌로 갚아야 할 보충 의무가 없을 때만 가능하다. 보관 계좌는 목록에서 숨고 새 거래를 받지 않지만, 과거 거래 기록은 그대로 남는다. 잔액이 남은 계좌는 먼저 이체로 0원을 만든 뒤 보관한다.
- 현황 카드의 잔액 캐시는 언제든 원장 합계와 재검증 가능해야 한다.

## 8. 보안 경계

초기 스캐폴드는 **인증 없는 로컬 전용 데모**다. Compose는 호스트 loopback에 포트를 바인딩한다. 외부 공개 전 사용자 인증, owner_id 스코핑, 권한, CSRF 보호, TLS, rate limit, 감사 로그가 반드시 필요하다.
