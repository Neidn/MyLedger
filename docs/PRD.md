# 내 가계부 제품 요구사항 명세 (PRD)

**프로젝트** 내 가계부 (`my-ledger`) · **버전** 1.0 · **일자** 2026-11-11 · **초기 사용자** 개인(향후 다중 사용자 가능)

제공된 스크린샷은 기능 참고용이며, 해당 앱의 이름·상표·디자인 자산을 프로젝트에서 재사용하지 않는다.

## 1. 문제 정의

여러 은행/저축 계좌와 선결제 플랫폼에 자금이 분산되어 있다. 단순 가계부는 계좌 간 이체, 할인 충전, 저축자금 임시 사용을 실제 소비와 혼동하거나 다음 급여일에 채워야 하는 금액을 계산하지 못한다.

## 2. 목표 및 비목표

**목표**
- 1개의 대시보드에서 계좌 잔액, 실제 소비, 남은 예산, 예정 비용, 보충 예정액을 구분해 보여준다.
- 자금 이동과 소비 기록을 분리해 중복 지출을 막는다.
- 급여일을 기준으로 자유 소비 가능 금액과 부족 위험을 예측한다.
- 할인 충전된 선결제 금액의 액면 잔액·실질 부담액·혜택 사용액을 추적한다.
- SQLite 단일 배포로 시작하고 데이터 저장 엔진을 교체 가능하게 한다.

**초기 비목표**
- 금융 계좌 직접 연동 및 자동 은행 인증, 전자결제 처리, 대출 심사, 복식 회계 재무제표, 세무 신고.
- 다중 기기 동시 실시간 협업과 클러스터 운영.

## 3. 핵심 사용자 스토리

1. **다중 계좌**: 나는 여러 계좌의 잔액과 자산 합계를 보고 싶다. 목적자금/선결제는 일반 현금과 구분되면 좋겠다.
2. **정확한 소비**: 생활비 통장→여행비 통장 이체는 소비가 아닌 이동으로 집계되길 원한다.
3. **선결제 충전**: 9만 원에 10만 원 충전 시 충전액 10만 원 및 혜택 1만 원이 기록되길 원한다.
4. **선결제 사용**: 3만 원을 쓰면 소비 3만 원, 할인 배분 기준 실질 부담 2.7만 원으로 분석되길 원한다.
5. **임시 인출**: 여행비 통장에서 20만 원을 빼서 쓰고 다음 급여일에 다시 채워야 함을 확인하고 싶다.
6. **부분 보충**: 5만 원을 보충해도 나머지 15만 원이 계속 추적되길 원한다.
7. **급여 주기**: 23일/25일 등 급여 주기에 맞춘 예산을 보고 싶다.
8. **고정비**: 월 정기 결제 예정일, 예상 금액, 실제 결제 여부를 구분하고 싶다.
9. **현금흐름**: 다음 급여일까지 확정/예정/추정 입출금에 따라 잔액이 어떻게 바뀔지 보고 싶다.

## 4. 주요 화면

| 화면 | 필수 요소 | 상태 |
|---|---|---|
| 홈 | 현재 가용 현금, 은행/선결제 구분, 이번 주기 사용 가능 금액, 보충 경고, 예정 지출 | 초기 계좌/요약 카드 구현, 나머지 후속 |
| 거래 | 수입/지출/이체/선결제 충전 입력, 날짜, 항목, 계좌, 보충 지정 | 초안 구현 |
| 계좌 | 계좌별 잔액/유형/목적자금/미보충액 | 초기 목록 구현 |
| 통계 | 주기별 수입·소비·차액, 예산 대비, 이전 주기 비교 | 후속 |
| 계획 | 정기입출금, 목표별 적립, 보충 일정, 미래 잔액 차트 | 초기 보충 목록 구현, 예측 후속 |

## 5. 기능별 상세 조건

### 계좌
- 유형: `bank`, `savings`, `cash`, `prepaid`. `credit`(대출/마이너스 통장)은 후속 모델에서 별도 부채 의미를 명확히 정의한다.
- 계좌 최초 생성 시 기초잔액을 **개시 거래**로 남긴다. 잔액만 임의 수정하지 않는다.
- 보충 대상은 계좌 또는 목적자금으로 지정할 수 있다(목적자금 후속).
- 계좌 보관 상태 변경은 거래 삭제 없이 가능해야 한다(후속).

### 거래
- 수입, 지출, 이체, 선결제 충전, 보충 상환을 구분한다.
- 기록에는 금액, 원화, 발생일, 메모 및 선택 카테고리를 포함한다.
- 입력 오류가 있으면 잔액이 일부만 변경되어서는 안 된다.
- 실수 정정/취소는 역거래 + 새 거래 방식(후속)으로 감사 가능하게 만든다.
- 동일 요청 재전송 방지를 위해 idempotency key 지원을 고려한다(초기 코드 지원).

### 선결제
- 실결제액(`paid`)과 충전 액면(`face`)을 함께 기록한다.
- `bonus = face - paid`, `bonus >= 0`을 전제로 시작한다.
- 충전 묶음(lot)별 원금과 혜택, 만료일을 저장한다.
- 충전금 소비 시 FIFO와 부분 사용 비례배분 원칙 사용. 플랫폼별 다른 소진 규칙은 후속 확장.
- 만료/환불/취소는 반드시 별도 거래를 남긴다(후속).

### 자금 보충
- '임시 인출'로 표시한 계좌 간 이체에만 보충 의무를 자동 생성한다.
- 원계좌, 차입 이동의 수취 계좌, 최초 인출액, 누적 보충액, 미보충액, 기한을 추적한다.
- 자동 추천 보충액과 수동 승인된 확정 이체를 구분한다.
- 일반적인 목표 잔액 부족분은 보충 의무가 아니다.

### 예산·예측
- 급여 주기와 달력 월간 주기 중 선택 가능(초기 기획).
- 현금흐름과 소비 예산을 별도로 예측한다.
- 확정 거래·예정 거래·통계 기반 추정 거래를 별도 상태로 표시한다.
- 가용 금액에서 보호된 목적자금과 보충 예정액을 구분해서 표시한다.

## 6. 비기능 요구사항

- **정합성**: 거래별 원장 합계 0, 계좌 잔액은 원장 기준. 중복 전송/부분 실패에 의한 이중 기록 방지.
- **보안**: 인터넷 접근 가능 환경에서는 인증/권한 및 TLS 구현 전 배포 금지. 개인정보·계좌번호는 초기에 저장하지 않아도 사용 가능하게 설계.
- **운영**: 단일 Docker Compose / 단일 SQLite 파일 / 로컬 영속 볼륨. 복구 가능한 백업 보유.
- **확장성**: 도메인 로직에서 SQL/DB 패키지 import 금지. DB 교체는 Adapter 및 스키마/이관만 변경.
- **UX**: 모바일 우선, PC 2열 대시보드, 한국어 및 원 단위 표시.
- **시간**: 표시 날짜는 `Asia/Seoul`, 영속 이벤트 타임스탬프는 UTC ISO 형식. 예정일은 `YYYY-MM-DD` 지역 날짜 문자열.

## 7. MVP 인수 테스트

1. 90,000원으로 100,000원을 충전하고 30,000원 쓰면 잔여 70,000원, 소비 30,000원, 비례 배분 실질 부담액 27,000원으로 계산된다.
2. 여행비 계좌에서 생활비로 200,000원을 이체하면 당기 소비는 증가하지 않고 보충 의무는 200,000원이다.
3. 생활비에서 여행비로 50,000원을 보충하면 미보충액은 150,000원이다.
4. 정기비용이 예정에서 확정으로 바뀌어도 미래 현금흐름에서 2번 차감되지 않는다.
5. SQLite 백업 사본을 별도 환경에서 복원해 계좌 잔액/거래 수/원장 합계를 확인한다.

## 8. 확정이 필요한 선택 사항

- 여러 선결제 플랫폼이 각기 다른 혜택 사용/환불 규칙을 가질 경우 어떤 정책을 적용할지.
- 자동 보충 알림만 할지, 자금 보충 거래를 자동 생성할지(권장: 사용자 승인 후 확정).
- 신용카드 및 마이너스 통장의 채무/결제일까지 포함할 시점.
- 가족 공동 관리와 사용자 계정 로그인 도입 시점.
